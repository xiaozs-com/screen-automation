# 结束处理与停止

流程正常完成、异常停止或用户停止时，可执行一次已声明的收尾。
查询 `workflow.lifecycle@1`，并在基本信息声明 `引擎能力：workflow-lifecycle@1`。

## 结束处理

收尾可保存摘要、整理结果和验证已完成的输出。账号授权、支付等高风险操作不能放在收尾中；
需要用户操作时保留待办与现场，明确报告尚未完成。结束处理的时间限制不能用来绕过人工交接。

```text
## 结束处理
- 执行：步骤【保存摘要】、步骤【投递结果】、步骤【确认投递】
- 超时：120 秒

## 执行步骤
### 保存摘要
- 用途：结束处理
- 执行：执行程序扩展【save_summary】

### 投递结果
- 用途：结束处理
- 执行：执行程序扩展【publish_results】

### 确认投递
- 用途：结束处理
- 如果：程序扩展【publish_succeeded】
- 则：继续下一步
- 否则：停止流程
```

上述为收尾配置片段；扩展入口和验证函数须在流程“程序扩展”中声明并实际实现。

使用已声明的步骤名称，不写应用专属逻辑到主程序。步骤会自动标记为结束处理，
正常业务路径会跳过它们；`用途：结束处理` 是可选的显式说明。
执行顺序以 `结束处理 → 执行` 列表为准，平台在终止时执行一次，不跟随步骤的普通成功跳转。
分支仅支持“否则停止流程”的验证形式，不能从结束处理跳回业务循环。

成功加载并开始运行的流程，无论正常完成、异常终止、用户首次点击停止，
都会进入结束处理。尚在 VLM 或人工等待中的流程还未终止，不会每次暂停都投递。
投递失败仍尝试执行后续确认步骤；错误保存在运行状态 `finalization.results` 和日志。
正常流程收尾失败会报告失败；有原始异常时保留原始终止原因，另记收尾失败。
收尾错误不递归调用 VLM，也不无限等待用户。

首次“停止”请求合作式正常停止；显示“正在结束处理”。
收尾使用独立取消信号，原来的停止请求不会立即把它取消。再次“停止收尾”才取消收尾，
若合作式取消仍不能结束，可强制终止任务。任务管理器强杀、断电和未成功加载的流程无法保证收尾。

总超时默认 120 秒，可设 1～3600 秒。SDK 检查点和等待受此总时限约束，
外部工具调用本身也必须设置超时；不要在扩展里写不检查停止的无限循环。
纯文件、网络等收尾允许在桌面不可用时继续，屏幕和键盘操作仍检查桌面可用性与既有授权。
`变量【结束状态】` 包含 `reason` 和 `error`，供摘要区分正常完成、停止和出错。
Python SDK 的 `cleanup(ctx, reason)` 也使用同一停止隔离机制，默认 120 秒。

## 显示顺序

流程窗口优先按“锚定窗口 → 执行步骤 → 结束处理 → 参数”展示已有内容；流程源码中的章节顺序不影响这个阅读顺序。

## 实际停止状态与失败诊断

发出停止请求不等于进程已退出。`stopping` 表示仍在停止，`finalizing` 表示收尾；继续读取运行状态，
不要看到 CLI 请求成功就报告停止完成。强停身份无法核验或结束失败时可返回 `stopped:false`，
保持 stopping 并记录 `stop_force_failed`；保留诊断，不按旧 PID 强杀其他进程。
尚未运行的排队任务直接取消，不为停止而启动。强杀、断电无法保证结束处理完成。
