# 流程异常处理系统规则

更新日期：2026-10-16。本文件记录当前源码的系统规则，作为开发、流程编写和回归验收的统一入口。
不表示旧安装包已经支持全部能力；安装版应先查询 `cli capabilities`。

## 一、三种不同的情况

| 情况 | 处理原则 | 是否提交 VLM |
| --- | --- | --- |
| 正常业务结果：扫描完成、未找到项目、内容过期、已存在、达到采集上限 | 流程用正常分支记录结果、跳过或结束 | 否 |
| 已配置的例外异常：特定步骤出现明确的错误类型或错误文字 | 按例外规则跳过、跳转或停止业务步骤 | 否 |
| 未知页面、遮挡、操作效果无法确认、识别失败等执行异常 | 保存现场，诊断、恢复或等待用户 | 有可用 Agent 和截图时提交 |

“没采集到全部内容”不必然意味着执行出错。业务正常结束条件应写在独立流程中，
不能依靠不断抛异常、重复扫描或反复请求 VLM 来决定何时结束。

## 二、从步骤失败到恢复的判断顺序

1. 执行动作并验证，先使用步骤已声明的有界等待、检查或重试。
2. 用户主动停止直接进入终止路径，不交给 VLM，也不被例外规则拦截。
3. 其他错误先匹配“例外异常”。命中时执行其处理方法并记录，不进入 VLM 或人工等待。
4. 未命中例外时进入异常恢复机制；启用 Agent 接入的托管流程默认有平台兜底，
   不要求每个流程都写一遍“异常处理”。旧步骤级恢复配置仍保持兼容。
5. 有效现场交给 VLM，一次返回异常分类以及多个观察字段；优先使用流程已配置的恢复方法。
6. 没有匹配恢复规则，但原步骤声明了“仍失败跳到步骤”时，保留这条处理路线，
   不能仅因分类为“未知”便丢弃原来的跳过或返回逻辑。
7. 无匹配方法和已声明路线时，可校验并执行模型提出的一次关闭临时遮挡的单击；
   没有可靠方案、复核失败或次数用尽，则保留进度等待用户。

后台输入拒绝和平台致命验证错误只做只读诊断，不自动恢复动作，不改变权限或前后台模式。
例外规则只能决定流程走向，不能使被拒绝的输入获得授权。
无法取得有效截图时记录原因并等待，不要求模型猜测锁屏、关闭窗口等不可见画面。
独立脚本若没有运行管理器和继续入口，则报告需要人工处理的错误。

## 三、VLM 的职责与边界

- 返回 `category` 和 `observation`；观察字段可包含置信度、理由、菜单状态等多个结果，
  不限于一个“是/否”。分类及理由应返回给用户和调用方，不能只显示一句“未知”。
- 默认读图超时为 360 秒，允许 Agent 处理较慢；超时不是立即丢弃流程进度的理由。
- 已配置方法优先。临时建议只允许关闭遮挡的一次坐标单击，要求置信度至少 0.95、
  坐标在现场范围内、窗口身份和大小未变，并沿用既有 SDK 授权。
- 不执行模型任意代码，不由模型临时授权输入，不自动执行提交、删除、发送等业务操作。
- 建议单击后等待 2 秒，再截图复核；明确恢复且置信度至少 0.95 才自动继续。
- 不持续后台读图。异常机制由步骤执行失败触发，不能保证在画面变化的瞬间发现异常。

## 四、异常处理是平台子过程

进入恢复时，平台保存原步骤、窗口基准、操作区域和返回方式。
处理块结束后由平台按保存的返回点返回，不要求流程作者额外编写“下一步”才能退出恢复块。

默认“自动返回”先验证原步骤是否已经完成：已完成便沿成功路线继续，避免重放点击；
未完成才重新执行原步骤。显式重试、继续下一步和指定跳转仍有效。
异常消失与业务完成是两件事：默认使用步骤验证，不额外调用 Agent；仅规则明确配置“恢复复核：Agent”时读图复核异常消失。
也可配置“恢复复核：人工确认”。返回后的原步骤验证业务结果。
复制菜单等临时坐标失效时，应通过规则的“恢复后”跳到重新准备和定位的步骤，不直接重放旧坐标。

统一配置为 `恢复入口：出错步骤`（默认）或 `恢复入口：步骤【准备步骤名称】`。
旧字段“恢复后”兼容保留，两者不能同时配置。平台在进入处理时保存入口，
自动恢复与人工继续都使用该保存值；日志和详情显示“出错步骤 → 恢复方法 → 恢复入口”。
运行状态 `exception_recovery` 可供外部 Agent 查询；返回后标记为 returned。

恢复动作失败仍可诊断和等待，但不递归重放自动点击。人工处理后继续，先复核当前画面。
普通动作步骤可被借用为恢复子调用；只执行其动作、等待和验证，不跟随其正常成功跳转。
复杂恢复使用专门的“用途：异常处理”步骤块。

“最多检查 N 次”只重复验证，不重放输入；“重试”才重复动作，数字和参数写法一致。
退出图片等非幂等操作应拆成“点击一次”和“等待验证”，避免再次打开图片。

## 五、人工等待与记录

等待时保留步骤、变量和已有结果，不从头重跑。主窗口有醒目提示，详情窗展示完整脱敏的
VLM 结果和日志；用户处理目标应用后点击“继续”。等待没有自动超时，用户可主动停止。
人工继续时若原操作窗口句柄已经失效，平台按原锚点声明重新请求用户确认窗口，
保留标题、进程等选择限制；确认后更新该锚点及其别名的窗口和坐标基准，再重试原步骤。
不自动启动应用、不重复打开页面、不清空业务变量；不能选用另一个已绑定锚点的窗口。
窗口仍有效时不重复选窗，页面异常继续沿原恢复与验证机制处理。
采集开始或恢复时关闭详情窗，防止其遮挡目标并污染 OCR。

有可采集窗口的失败现场保存截图及关联信息；截图失败保留原始异常，不用截图错误覆盖它。
用户主动停止不作为失败现场强制截图。VLM 记录保存为现场旁的 `.vlm.json`，
运行状态通过 `exception_observation` 返回；日志和状态仍需脱敏。
新 VLM 结果包含带时区的 `recorded_at`，界面按本机时区显示记录时间；旧记录缺少时间时明确标注。
详情和完整日志打开或刷新后默认滚动到末尾，详情末尾重复显示最新运行状态、步骤及暂停或结束原因，
便于先查看最近问题。截图失败应显示真实原因，不把仍在等待的运行描述为已经终止。

Python SDK 使用 `ctx.step.perform` 保留可重试的步骤边界。
任意 Python 语句抛错并不意味着平台可以跳回那条语句：无可恢复边界时诊断并等待，
明确说明继续只能重新诊断，不偷偷重跑整个脚本。

## 六、终止与结束处理

正常完成、例外规则停止、实际异常终止，以及用户首次点击“停止”，均应在实际终止时
执行已配置的“结束处理”一次。VLM 处理和人工暂停还没有终止，不会每次暂停都投递结果。

首次停止是合作式停止请求，不是强制结束进程；不能等 2 秒便自动强杀。
正常停止不打印“工作流执行异常”或 traceback；截图提示被停止取消也不记为警告。
窗口激活等辅助调用必须原样传播 WorkflowStopped；在分派其他异常前再次检查停止请求，
若已请求停止则直接进入结束处理，不提交 VLM。已有异常先发生、尚未收到停止请求的情况仍走异常处理。
收尾隔离原停止信号，界面显示正在结束处理；再次“停止收尾”可中断，
若仍无法合作式停止，可强制结束。强杀、断电、流程未成功加载无法保证收尾。

结束步骤按配置顺序执行，不跟随普通成功跳转；一个步骤失败仍尝试后续步骤，
例如投递失败后仍检查投递结果。收尾不递归进入 VLM 和无限人工等待。
结果记录在 `finalization.results`；有原始错误时保留原始错误并另记收尾错误，
正常完成却收尾失败则报告失败，不能声称数据投递成功。

总超时默认 120 秒，可配置 1～3600 秒。该限制依靠 SDK 检查点合作执行，
外部工具还需自身超时；不能保证中断不检查停止的任意 Python 死循环。
文件和网络收尾可在桌面不可用时继续，屏幕输入仍受桌面状态和授权约束。
Python SDK 的 `cleanup(ctx, reason)` 使用同一停止隔离机制。

## 七、配置与界面约定

流程规则、目标应用的页面判断和业务投递都属于独立流程，不写入平台默认业务逻辑。
阅读与编辑界面先显示“锚定窗口”“执行步骤”，再显示异常处理、例外异常、结束处理等配置。

## 八、回归与发布核对

系统修改至少核对：正常完成不触发 VLM；例外规则精确匹配；未知异常能诊断并等待；
恢复返回不重复已完成点击；恢复失败不递归自动点击；人工继续保留进度；
首次停止执行收尾；再次停止可取消收尾；投递失败仍尝试确认；结束处理只执行一次；
锁屏不放宽屏幕输入权限；运行记录保留原错误和收尾结果。

对应测试入口包括 `tests/test_flow_exception_policy.py`、`tests/test_workflow_lifecycle.py`、
`tests/test_stop_collection.py`、`tests/test_run_instances.py` 和 `tests/test_recovery_details.py`。
测试通过、源码启动、安装包交付、真实 Agent 联调和真机验收分别记录，不互相替代。
