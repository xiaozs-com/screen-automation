# 例外异常与结束处理

完整判断顺序见[流程异常处理系统规则](workflow-exception-system.md)。

先检查 `cli capabilities` 有 `workflow.lifecycle@1`，并在流程基本信息声明
`引擎能力：workflow-lifecycle@1`。这是新版主程序能力，旧安装包不支持此语法。

## 例外异常

```text
## 例外异常
### 规则【跳过已确认的不适用内容】
- 步骤：步骤【验证内容】
- 错误包含：内容类型已确认不适用
- 处理：跳到步骤【下一项】
- 最多次数：100 次
```

可选字段 `错误类型：ScreenStateMismatch` 按异常类名匹配，包含父类；`错误包含` 是
区分大小写的普通文字，不执行正则或代码。类型和文字至少声明一个；同时声明时均须满足。
`步骤` 可省略，省略时在整个流程生效，宜谨慎使用。

例外匹配先于 VLM，不截图提交模型、不进入人工等待；仍记录原始错误和规则。
`处理` 可为 `继续下一步`、`停止流程`、`跳到步骤【名称】`。不支持无界重试；
每规则默认最多 10 次，可设 1～100 次，耗尽后停止业务步骤并执行结束处理。
用户主动停止不由例外规则拦截；SDK 权限和前后台输入限制仍然有效。
没有匹配例外时，保留原来的 VLM、已配置恢复方法和人工参与机制。

## 结束处理

```text
## 结束处理
- 执行：步骤【保存摘要】、步骤【投递结果】、步骤【确认投递】
- 超时：120 秒

## 执行步骤
### 投递结果
- 用途：结束处理
- 动作：执行程序扩展【publish_results】

### 确认投递
- 用途：结束处理
- 如果：程序扩展【publish_succeeded】
- 则：继续下一步
- 否则：停止流程
```

使用已声明的步骤名称，不写应用专属逻辑到主程序。步骤会自动标记为结束处理，
正常业务路径会跳过它们；`用途：结束处理` 是可选的显式说明。
执行顺序以 `结束处理 → 执行` 列表为准，平台在终止时执行一次，不跟随步骤的普通成功跳转。
分支仅支持“否则停止流程”的验证形式，不能从结束处理跳回业务循环。

成功加载并开始运行的流程，无论正常完成、例外规则停止、异常终止、用户首次点击停止，
都会进入结束处理。尚在 VLM 或人工等待中的流程还未终止，不会每次暂停都投递。
投递失败仍尝试执行后续确认步骤；错误保存在运行状态 `finalization.results` 和日志。
正常流程收尾失败会报告失败；有原始异常时保留原始终止原因，另记收尾失败。
收尾错误不递归调用 VLM，也不无限等待用户。

首次“停止”是合作式正常停止，不再在 2 秒后自动强杀进程；显示“正在结束处理”。
收尾使用独立取消信号，原来的停止请求不会立即把它取消。再次“停止收尾”才取消收尾，
若合作式取消仍不能结束，可强制终止任务。任务管理器强杀、断电和未成功加载的流程无法保证收尾。

总超时默认 120 秒，可设 1～3600 秒。SDK 检查点和等待受此总时限约束，
外部工具调用本身也必须设置超时；不要在扩展里写不检查停止的无限循环。
纯文件、网络等收尾允许在桌面不可用时继续，屏幕和键盘操作仍检查桌面可用性与既有授权。
`变量【结束状态】` 包含 `reason` 和 `error`，供摘要区分正常完成、停止和出错。
Python SDK 原有 `cleanup(ctx, reason)` 也使用同一停止隔离机制，默认 120 秒。

## 显示顺序

流程阅读和编辑页固定先显示“锚定窗口”“执行步骤”，再显示异常处理、例外异常、
结束处理及其他辅助配置；原文件章节顺序不影响这个阅读顺序。
