# 自动化流程开发标准

本文定义的自动化流程由屏幕自动化小助手桌面端安装和运行。

## 观察、执行、验证

新增流程使用语言3，首先阅读 [Agent 阶段与步骤内失败处理](workflow-agent-phases.md)。
先查询 `cli capabilities` 的 `workflow.agent-phases@1` 及 `cli workflow schema steps`，按当前接口编写并校验。
每步按观察、执行、验证组织，每个阶段可以选择程序或 Agent；文字输入走文本能力，区域截图要求视觉能力。
失败处理和下一步就在步骤内，不生成流程级异常处理、例外异常或 VLM 专用字段。
Agent 观察/验证/失败判断只读，只有执行阶段的明确授权可改变屏幕；定位结果经窗口、范围及画面校验后由程序点击。


本文是“屏幕自动化工程师”创建、修改和修复流程时必须遵守的当前标准。实际平台能力仍以
`cli capabilities` 返回值为准。

Windows 先执行 `$AppCli = & .\scripts\workflow_dev.ps1 -Action cli-path`，macOS 先执行
`APP_CLI="$(bash ./scripts/workflow_dev.sh cli-path)"`；后续示例中的 CLI 命令均调用该原生路径。

## 可选组件前提

编写前核对当前组件目录、`cli capabilities` 和 `cli access list`，需要组件的能力必须已安装、已激活、已启用且 `effective: true`。组件名单可扩展，不能只检查浏览器增强或 Agent 接入。未满足条件时，不推荐直接使用、不把依赖它的流程描述为可运行；只提醒可选扩展及软件界面获取授权码、激活和安装的路径。已有核心能力不应误归为付费组件。用户明确要求准备未来启用的流程时可生成草稿，但须标明前提，当前不运行。

## 新流程包

```text
my-workflow/
├── workflow.md
├── workflow.py   # 可选：仅必要的局部算法或连续交互事务
├── assets/       # 可选
├── tests/        # 可选
└── README.md     # 可选
```

`workflow.md` 是用户可读规则和步骤的主要来源。只有重复列表、复杂分类、多窗口关联等无法用标准
命令直接表达的流程，才可以增加一个根目录 `workflow.py`。不得创建 `workflow.json`、
`__pycache__`、`*.pyc`、日志、结果、调试截图或编译缓存。

## 先选择包结构

只要当前安装版本的标准命令能够完整表达，就只创建 `workflow.md`。下列情况只有在标准命令、
分支、有界循环或交互模板仍无法表达所需局部逻辑时，才增加 `workflow.py`：

- 需要遍历动态数量的可见列表项；
- 需要组合 OCR、颜色、轮廓或多个窗口证据进行业务分类；
- 需要维护流程自己的历史去重或逐项生成对象结果；
- 有限条件与重复语法仍无法清楚表达，但所需底层能力已经由 `ctx` SDK 提供。

“步骤多”“代码写起来方便”不是增加程序扩展的理由。程序扩展只能调用 `ctx`，不能导入
`pyautogui`、`cv2`、窗口系统 API、网络下载或命令执行模块。

## 可见步骤优先

`workflow.md` 的“执行步骤”是业务流程的实际编排入口，不只是说明目录。按用户能理解和验证的
业务阶段拆分；点击、等待、分支、有界循环、验证和输出，只要当前流程语言支持，就放在可见步骤中。
不得仅因流程复杂或某个逻辑不能写成单一命令，就把整条流程放进 `.py`；也不得添加空说明步骤，
最后仍由单个扩展入口包办所有业务。步骤应体现动作顺序、成功标志和失败边界，支持阶段调试和定位失败。

扩展只负责无法表达的局部算法，或拆开会破坏临时菜单、焦点或时序的连续交互事务。先检查交互模板
是否足够；需要扩展时登记具名入口，在对应业务步骤调用并说明用途、返回结果、成功验证和失败边界。
合并连续操作须说明已观察到的原因，只合并必要范围；事务前后的读取、判断和输出仍优先保留为可见步骤。
关键页面标志不确定时跳过或停止，不能以按钮出现时间短为由假定按钮已出现或盲点。

可调坐标、文字、等待、次数和业务规则仍放在 `workflow.md`。维护已有单入口流程时先评估状态共享、
窗口切换和时序，再按需拆分并验证；不为凑步骤数添加空步骤。交付前检查：主要阶段是否实际可见，
每个扩展是否确有必要、范围是否足够小、输入输出和失败边界是否清楚。

## Agent、联网、文件与外部工具

流程可以调用 Agent 和其他工具，不是一概禁止联网或生成文件。语言 3 各阶段的 `方式：Agent` 通过配置的 Agent Provider 接入，可以一次返回多个结构化判断；浏览器联网使用 `ctx.browser`。结果、截图和下载分别使用已有公开接口。

文件与工具接口包括 `ctx.files.read_text/read_json/write_text/write_json`（声明读取文件、写入文件）及 `ctx.tools.run(executable, arguments=[...], timeout=60)`（声明控制应用）。编写前查询安装版本 `cli workflow sdk` 是否包含这些方法。文件相对路径以流程输出目录为基准；工具返回 `exit_code/stdout/stderr/truncated`，检查退出码、完整输出和业务结果后才继续。

HTTP/API、文档生成脚本和有命令行入口的其他 Agent 可作为外部工具调用；MCP/App 工具须由实际连接它的 Agent 或真实工具入口完成，不能直接虚构工具名称。启动接口 `ctx.app.launch_application` 只请求启动，不返回业务成功；需要执行结果时优先使用 `ctx.tools.run`。不要再用剪贴板作为外部工具的默认返回通道。

公共能力受清单权限和用户任务授权约束。不要把“禁止扩展直接 import 网络/文件/进程库”解释为“小助手不能联网/生成文件/调用工具”。不得将原始凭据写入流程、命令参数、日志或结果。

## 智能阶段与受信任代码

观察、执行、验证都可选程序或 Agent；观察结果可指导程序执行，或作为 Agent 执行输入。
Agent 不限于异常读图：正常步骤也可理解、定位、提取、执行和验证。详细语法及严格返回字段见
[阶段契约](workflow-agent-phases.md)，机器格式用 `cli workflow schema steps` 查询。

语言 3 失败路线与明确错误条件写在步骤内；未声明处理时安全停止。
Python 扩展按当前用户权限执行，是受信任代码。导入/AST 检查及 SDK 权限不构成系统沙箱，
`ctx.files` 的 base 仅解析相对路径，不隔离绝对路径。只安装自己编写或来源可信的流程，详见 [信任边界](workflow-trust.md)。
SDK 公共接口仍是工程规范，不应绕过 SDK 控制屏幕或进程。

## 文件骨架

以下示例只展示格式；窗口标题、区域、文字和完成标志须由当前观察校准后才能运行。
点击后采用“最多检查”避免重放保存。智能观察和智能执行的完整示例见 [阶段参考](workflow-agent-phases.md)。

```markdown
<!-- 屏幕自动化流程语言：3 -->

# 示例：确认并保存

## 基本信息

- 标识：save-current-item
- 版本：0.1.0
- 用途：确认页面后点击保存并检查结果
- 目标系统：Windows、macOS
- 权限：读取屏幕、点击屏幕
- 引擎能力：agent-phases@1
- 创建者：Agent

## 参数

- 内容区域：RECT(left=10,top=20,right=300,bottom=400)

## 锚定窗口

- 标题包含：示例程序
- 找不到时：提示用户重新选择

## 坐标与区域

- 区域【内容】：操作区域【锚定窗口】内 参数【内容区域】

## 执行步骤

### 保存并确认

- 在：区域【内容】
- 观察：区域【内容】出现文字【保存】
- 执行：点击区域【内容】中的文字【保存】
- 验证：区域【内容】出现文字【已保存】
- 失败：
  - 最多检查：3 次
  - 间隔：1 秒
  - 仍失败：等待人工
- 下一步：继续下一步
```

必需章节：基本信息、锚定窗口、坐标与区域、执行步骤。参数、规则、交互模板、程序扩展、输出按需声明。
语言 3 不接受流程级“异常处理”“例外异常”；结束处理需检查 `workflow.lifecycle@1` 并声明
`workflow-lifecycle@1`。新建和保存统一使用 `## 执行步骤`，同一文件不能同时包含 `## 流程`。
标识使用 3～64 位小写字母、数字和连字符；版本使用语义化版本。创建者写实际 Agent 产品名。


## 坐标和窗口

- `POINT(x=,y=)` 是点；`RECT(left=,top=,right=,bottom=)` 是区域。正文坐标永远相对于当前操作区域左上角；绝对屏幕坐标不得持久化。
- 锚定窗口只是第一个操作区域，不是全流程排他锁。操作区域绑定窗口作为坐标锚点；窗口移动、
  缩放或排列后坐标跟随更新。执行每个步骤前，底座自动激活该步骤 `在` 指定的窗口，窗口即使
  重叠也能切换操作。新窗口使用：
  `新窗口：等待新出现的窗口，标题包含【文字】，登记为操作区域【名称】`。
- `标题包含` 和 `首选进程` 都可省略。唯一候选自动确认；没有筛选条件或多个候选时由底座显示
  虚线框让用户选择，流程不写确认机制；没有候选且声明 `应用`、`找不到时：启动应用` 时直接启动
  并等待。`应用` 是 Windows `.exe` 文件名且未另写 `首选进程` 时，该文件名是严格进程条件，
  不得退回到只有标题相同的其他应用窗口。
- 跨应用动作：`打开应用【应用名或可执行文件】`；打开后用 `新窗口` 登记为命名操作区域。
- 打开已有本地文档：`打开文件【固定路径】`、`打开文件【参数【文档路径】】` 或
  `打开文件【变量【文档路径】】`；使用系统默认关联应用，不经过 shell。流程必须声明“读取文件、
  控制应用”，日志和结果不得记录完整路径；后续需要操作新窗口时用 `新窗口` 登记。
- 窗口命令：`切换到操作区域【名称】`；`排列窗口【区域一、区域二】为【并排】`。排列还支持
  `上下排列`、`网格`、`二乘二`，目标必须是二至四个已登记操作区域。
- 纯浏览器增强步骤可以省略 `在`。它们操作受管浏览器会话对象，不得把标题相同的普通
  Chrome/Edge 窗口当作受管会话。流程主动打开并登记的新应用窗口默认继承锚定窗口的位置和
  大小；受管浏览器被发现后也强制应用该区域。显式排列窗口或指定其他布局时，以流程声明为准。
- `打开浏览器会话` 步骤中的浏览器元素 `观察` 在会话创建后作为就绪检查，不能先定位再打开。
  纯浏览器观察、验证和动作步骤均不要求桌面操作区域。
- 页面文字条件写成 `浏览器出现文字【文字】` 或 `浏览器未出现文字【文字】`；元素条件仅接受 CSS
  selector。登录等人工步骤写 `失败：等待用户继续`，复用主界面“继续”按钮触发立即复检。
  追加 `；10秒重试` 可同时启用定时自动复检；点击“继续”会提前唤醒，不必等到定时点。

## 统一数字类型

禁止在新流程中使用裸 `[]` 数字列表、`RATIO` 或 `RATIO_RECT`。字段中文名描述业务，数据类型用英文构造器或自描述裸值表达：

| 写法 | 裸值写法 | 含义 |
|---|---|---|
| `POINT(x=,y=)` / `RECT(left=,top=,right=,bottom=)` | 不支持 | 操作区域内的相对像素点/矩形 |
| `PIXELS(n)`、`COUNT(n)`、`SCROLL(n)`、`DURATION(1.5s)` | `90`、`30`、`-600`、`1.5s`（上下文明确时） | 像素、数量、滚动量、时长 |
| `PERCENT(40%)` | `40%` | 百分比；流程源码必须带 `%` |
| `PERCENT_RECT(left=0%,top=50%,right=100%,bottom=100%)` | 不支持 | 操作区域比例矩形 |
| `HSV(h,s,v)`、`HSV_RANGE(lower=...,upper=...)` | 不支持 | HSV 颜色与范围 |
| `SIZE_RANGE(width=42..68,height=42..68)`、`AREA_RANGE(40..600)`、`RANGE(0.72..1.35)` | 不支持 | 尺寸、面积与普通数值范围 |

`1.5s`、`800ms`、`40%`、`true`/`false` 自描述类型，可直接写；无单位的裸数字只在
字段上下文已知时使用，例如 `最多处理次数：30`、`在 点【名称】滚动 -600`。`SCROLL` 的数值
表示屏幕像素的滚动量，通常使用数百像素；不要使用 `9000` 这类远超单屏范围的值。纵向滚动中正值向上、负值向下；横向滚动中正值向右、负值向左。

动态列表行只使用 `ROW_Y`，表示当前识别到的列表行 Y 基线；没有 `ROW_CENTER_X`。比例、锚点和偏移属于规则或参数，不能藏进程序扩展。

文件关联；不得使用 shell、命令拼接或自行导入系统启动 API。

### 浏览器增强

浏览器增强是应用增强，不是执行者。步骤仍由 `engine` 执行，流程必须声明
`引擎能力：browser-enhancement@1`。Windows 可写 Chrome 或 Edge；macOS 当前只可写 Chrome。
可复用流程优先使用小助手的持久化受管会话；普通浏览器当前页面能由屏幕/UIA可靠完成时直接继续，
不因为它属于用户日常 Profile 而拒绝任务。需要 DOM 能力时使用受管会话，并保留已有登录状态。

一次性当前页面任务可使用桌面端顶层 `browser` CLI；可复用流程仍使用 `ctx.browser`。两者共享访问状态、
受管 Profile、唯一定位、会话对象和验证边界。顶层 CLI 应优先复用存活的受管会话；用户普通浏览器窗口无法
附着 DOM 时继续使用屏幕/UIA，任务确需 DOM 且屏幕路径不足时再由小助手打开同一网址。
组件不可用时按当前错误及设置界面诊断。

典型顺序是：打开或复用会话 → 导航 → 定位并保存对象变量 → 读取或操作对象 → 验证可见结果。
流程成功、失败、停止或等待用户后默认保留浏览器和普通应用窗口；只有执行步骤显式声明关闭或用户
手动关闭时才关闭。需要结束会话的流程在末尾写“关闭浏览器会话”。
定位要求唯一目标；零个或多个匹配都必须停止或进入有界恢复。下载只能保存到本次运行的受管下载
目录，流程不能指定任意系统目录。浏览器对象只在创建它的当前会话有效，不得跨会话复用。

用户目标是复制网页正文、列表、链接、表格或跨滚动区域内容时，优先使用浏览器增强。当前桌面端若在
`cli capabilities` 中声明 `ctx.browser.select_text` 和 `ctx.browser.copy`，使用以下语法：

```markdown
- 执行：浏览器选择变量【正文对象】内容
- 执行：浏览器复制变量【正文对象】字段【text】
```

选择要求 `操作浏览器`；复制同时要求 `读取浏览器` 和 `写入剪贴板`。复制字段只允许 `text`、`value`、
`href`，目标必须唯一、可见、属于当前会话且内容非空，单次 UTF-8 内容不得超过 1 MiB。日志和结果只记录
字段、字符数和验证状态，不记录正文。当前桌面端未声明这两个动作时，可以用 `browser.read` 后将明确字段
写入剪贴板完成“提取并复制”，但不得声称页面已经形成可见选区；不得用全页 `Ctrl+A` 或盲目拖拽模拟。

“帮我复制一下这篇文章的正文部分”应直接路由为：定位通用文章正文 → 保存唯一正文对象 → 选择正文 →
复制 `text` 字段。用户不需要提供 CSS selector。正文无法唯一识别时显示候选范围让用户确认，不能猜测。

程序扩展需要浏览器原子能力时，只能调用当前 SDK 的 `ctx.browser`：`open`、`navigate`、`locate`、
`find`、`read`、`click`、`fill`、`scroll`、`press`、`download`、`verify` 和 `close`；仅在当前
`cli capabilities` 明确列出时，才可额外调用 `select_text`、`copy` 等新增动作。调用方法必须与声明权限一致；
所有改变页面的调用仍放入 `ctx.step.perform()` 或受监督的 `ctx.debug.step()`。不得在 `finally` 或流程
清理阶段自动关闭会话；只有流程语义明确要求关闭时调用 `ctx.browser.close()`。不得直接导入 Playwright、
浏览器驱动或网络库。

权威签名和返回结构如下，不得猜测。先调用当前安装版本的 `cli workflow sdk` 或
`cli workflow schema sdk` 取得机器可读 JSON；以下内容用于阅读说明：

```python
ctx.browser.open(browser="chrome", area=None)       # {session_id, provider_id}
ctx.browser.navigate(url)                           # {success, action, data}
ctx.browser.locate(selector, text="", limit=1)     # list[{object_id, ...}]
ctx.browser.find(selector, text="")                # 唯一 {object_id, ...}
ctx.browser.find_article()                          # 唯一文章对象
ctx.browser.read(target, fields=("text",))         # {source, object_id, data:{...}}
ctx.browser.click(target); ctx.browser.fill(target, text)
ctx.browser.select_text(target); ctx.browser.copy(target, field="text")
ctx.browser.scroll(x=0, y=0); ctx.browser.press(key)
ctx.browser.download(target, filename="")
ctx.browser.verify(action, expectation)             # {passed, evidence, message}
ctx.browser.close()                                 # None
```

Markdown 浏览器步骤和后续程序扩展共享同一 `ctx.browser` 实例与受管会话。已有会话时扩展直接读取，
不得再次 `open()`；流程收尾默认保留会话，后续流程可复用。只有流程明确要求关闭时才调用
`ctx.browser.close()`；可用 `ctx.browser.opened` 判断当前上下文是否已有会话。

创建包含 `browser-enhancement@1` 的流程前，先确认当前 `cli capabilities` 列出
`workflow.browser-enhancement@1`，再确认 `cli access list` 中 `browser_enhancement.status.effective`
为 `true`。前者是动作契约，后者是授权、组件安装、平台可用性和启用状态；两者不能互相替代。使用
Agent 阶段时另核对 Provider 状态。所需组件未就绪时按 `reason` 和 `action` 解释缺失环节，
由用户按软件界面配置；不得保存、索取或代输授权码。

会改变页面状态的导航、点击、填写、下载、滚动和按键仍需操作前观察与操作后验证。结构化 DOM
结果可以参与定位和读取，但隐藏元素不能伪装成当前可见屏幕对象；关键结果优先用重新定位、重新读取
或屏幕证据交叉验证。组件缺失、浏览器缺失、会话失效或前台验证受系统限制时明确停止，不退化为
猜坐标或普通 Profile 操作。

### Agent 观察与执行

观察、执行、验证的嵌套字段均支持 `方式：Agent`。输入可为当前区域截图、文字或变量，
执行可读取 `变量【观察结果】`，验证可读取 `变量【执行结果】`。
Agent 定位后用 `执行：点击观察结果` 由程序校验并点击；也可在执行阶段声明任务交给 Agent。
屏幕操作须显式授权并有验证；未授权的文本执行可以整理、推理和返回数据。
完整示例、Provider 检查及结果格式见 [阶段参考](workflow-agent-phases.md) 与 [Agent 接入](agent-bridge.md)。

### 填写表单与运行期锚定

`填写表单` 用顿号分隔多个 `字段标签=值`。默认逐个以字段标签进行 OCR 定位；当输入框没有
可识别的占位文字、或 macOS 不适合依赖 Tab 顺序时，为每个字段写运行期定位修饰：

```markdown
- 执行：填写表单：锚定【用户称呼（选填）】偏移【0,42】用户称呼=演示用户、锚定【手机号（选填）】偏移【0,42】手机号=13800000000、锚定【请用一句话概括问题或建议】反馈标题=示例标题、锚定【建议写明使用场景】建议内容=示例正文
```

- `锚定【OCR文字】`：在当前操作区域内实时 OCR 查找该文字；可用框内占位文字，也可用输入框
  上方或旁边的稳定标签。
- `偏移【x,y】`：只可紧接 `锚定` 使用，表示从 OCR 文字中心向右/向下的相对像素偏移，用于
  从标签点入空输入框；不是固定屏幕坐标。必须先在真实页面确认偏移仍落在输入框内。
- `相对【OCR文字】右侧`（也可为左侧、上方、下方）：只可紧接 `锚定` 使用；在同一轮 OCR
  结果中选择与参照文字符合该方位的最近候选，用来消除“手机号”等在说明文字和字段标签中重复
  出现的歧义。例如：`锚定【手机号】相对【用户称呼】右侧偏移【0,42】`。
- `点【名称】`：使用已声明的命名点直接点击该字段；同一字段不能同时使用 `点` 和 `锚定`。
- `焦点文字【文字】`、`焦点点【点名称】` 与 `按序连填` 是整个表单的可选方式；`按序连填`
  依赖系统 Tab 焦点移动，macOS 上优先逐字段使用 `锚定`/`偏移`。

不得省略锚定而单独写 `偏移` 或 `相对`，不得为同一字段重复声明锚定、相对定位或偏移。运行时每个锚定都会重新
OCR；偏移点超出操作区域上下边界时，底座最多滚动 3 次，并在每次滚动后重新读取操作区域、重新
OCR 锚定。横向越界、锚点消失或仍然越界都会安全停止。不得把“滚动一下试试”写成无上限循环，
不得为了绕过停止而改成操作区域外的固定坐标。每次锚定成功后，底座会在实际 OCR 命中的文字框
上短暂显示虚线提示；用户应借此确认匹配到的是正确字段，再继续使用该流程。

## 交互模板

交互模板与交互锁共享“交互”前缀，是命名上的一对呼应概念，但机制上各自独立：交互锁协调多个
自动化流程，避免在弹菜单、确认等窗口期间互相插入操作；交互模板把“打开菜单→识别菜单项→点击→
必要时确认”这类连续交互，打包成一段由底座执行的复用事务。二者按需使用，并非强制配对。

何时使用：需要把一段连续交互打包为可复用动作、避免在 `workflow.py` 中重复实现时，用交互模板；
需要保护临时菜单/确认框窗口期不被其他流程插入时，声明交互锁；单一动作（点击、输入、滚动）
直接用动作命令。当前交互模板为 `上下文菜单操作`，章节标题必须写成 `上下文菜单操作【名称】`：
字段以本文件为准，也可用 `cli workflow schema templates` 输出当前引擎的权威字段清单。

```markdown
## 交互模板

### 上下文菜单操作【复制文章链接】

- 打开方式：右键
- 目标：点【文章菜单位置】
- 菜单区域：区域【文章快捷菜单】
- 菜单项文字：复制链接
- 等待菜单出现：DURATION(0.8s)
- 菜单未出现时：停止
- 确认：无需确认
```

字段只允许 `打开方式`、`目标`、`菜单区域`、`菜单区域2`、`菜单项文字`、`等待菜单出现`、`菜单未出现时`、`确认`、
`确认区域`、`等待确认出现` 和 `长按时长`。`打开方式` 只能是 `右键` 或 `长按`；`确认` 可写
`无需确认`，也可写 `点击文字【确定】` 或用顿号声明备选文字，如 `点击文字【确定、确认】`。
确认按钮名称需要由用户或运行环境调整时，写成 `点击参数【确认按钮文字】`；参数值同样可以用顿号
提供多个候选名称。
需要确认时必须声明 `确认区域`，可引用具名区域、使用带锚点的 `RECT(...)`，或使用
`PERCENT_RECT(...)`。只有在该区域识别到声明文字后才会点击；没有识别到则停止，禁止盲点。
模板名称不得重复，目标、菜单区域与具名确认区域必须属于同一操作区域。
`等待菜单出现` 与 `长按时长` 必须是 `DURATION(...)`，也可以写裸值（如 `0.8s`、`1.2s`）或 `参数【名称】` 交给用户校准；
两者省略时分别按 `DURATION(0.5s)` 和 `DURATION(1s)` 处理，`菜单未出现时` 省略时按 `停止` 处理。
`菜单项文字` 既可以直接写文字，也可以写 `参数【名称】`；运行时会读取该参数的当前值后再进行 OCR。
菜单文字也可以和确认按钮一样用顿号提供多个候选，例如 `菜单项文字：复制链接、复制地址`；运行时按
候选顺序识别，命中最先出现的文字。需要让用户或不同环境调整菜单名称时，应优先使用参数引用。
菜单可能向上弹出时，可增加 `菜单区域2` 声明第二个候选区域；底座先识别 `菜单区域`，未命中再识别
`菜单区域2`，两个区域必须属于同一操作区域。

动态列表行允许把模板目标和菜单区域直接写成带锚点的表达式，例如：

```markdown
- 目标：POINT(x=AREA_CENTER_X,y=ROW_Y)
- 菜单区域：RECT(left=AREA_CENTER_X,top=ROW_Y-33,right=AREA_RIGHT,bottom=ROW_Y+392)
```

这种模板必须由程序扩展在识别出当前行后调用，并传入本次运行的行锚点：
`ctx.templates.context_menu("复制当前链接", anchors={"ROW_Y": center_y})`。`AREA_CENTER_X` 是当前操作区域的
水平中心，由底座自动计算，因此长按点会保持原流程的水平位置。
`ROW_Y` 是当前处理行的 Y 基准；没有当前行上下文时不得猜测或复用旧值。纯 Markdown 步骤调用不会自动产生
`ROW_Y`，因此不能直接执行依赖 `ROW_Y` 的模板。

步骤中用 `执行：执行交互模板【复制文章链接】` 调用，程序扩展中用
`ctx.templates.context_menu("复制文章链接")` 调用，两者共用这一份 Markdown 声明。打开菜单、
识别菜单、选择菜单项和验证由底座包成一段交互事务，其他流程不会插入其间。

### Python 调用交互模板的契约

`ctx.templates.context_menu(name, anchors=...)` 使用与 Markdown 同一份模板声明：

- `anchors` 提供本次运行需要的动态锚点，例如 `{"ROW_Y": center_y}`；`AREA_LEFT`、
  `AREA_TOP`、`AREA_RIGHT`、`AREA_BOTTOM`、`AREA_CENTER_X` 由底座按模板操作区域自动补齐。
  模板引用了 `ROW_Y` 或自定义锚点而调用方未提供时，会抛出明确错误，不会静默使用错误坐标。
- `参数【名称】` 在运行时会从流程参数（`ctx.config`）解析；也可以直接写固定文字。
- 坐标表达式支持 `参数【名称】` 作为 x/y 分量，例如 `POINT(x=参数【行中心X】,y=ROW_Y)`，
  参数值是数字或标准锚点表达式；也允许调用方通过 `anchors` 传入自定义锚点名。
- 调用会自动包成交互事务，默认等待 30 秒，开始/结束说明使用模板名；需要与规则中声明的
  `交互锁开始`/`交互锁结束`/`等待交互锁` 对齐时，可传
  `start=rule["交互锁开始"], end=rule["交互锁结束"], timeout=ctx.values.duration(rule["等待交互锁"])`。
- 成功返回 OCR 命中的菜单项对象（含 `center`、`box`、`text`、`confidence`），有确认框时
  额外带 `confirmation`；菜单项或确认按钮未识别到时抛出 `ScreenStateMismatch`，模板未声明时
  抛出 `WorkflowFatalError`。

## 用户在场的交接步骤

账号登录、账号授权、身份验证、密码/验证码输入、支付、转账及其他高风险不可逆操作由用户在场亲自完成。
流程只准备非敏感内容并保留现场，到交接位置等待用户；不把高风险动作编入程序、Agent 执行、恢复或收尾。
用户完成后重新检查页面结果再继续。普通可撤销操作按任务直接推进。

## 可选目标与失败去向

OCR 成功执行但未找到可选目标、列表扫描结束等预期结果，用分支或明确失败去向表达。
截图、OCR 服务、窗口或权限错误不能冒充“无目标”。关键页面不确定时等待人工或停止。
语言 3 可用本步“失败”块配置有界重试、只验证检查，以及“仍失败”的程序/Agent 路线。
`重试` 重新观察并执行；`最多检查` 只验证，二者不能同写。智能判断仅选择作者声明的路线，
不能据模型建议执行任意代码、旧坐标或扩大权限。恢复后验证原步骤结果，发送等动作先判断是否已经完成。
具体字段见 [步骤内失败处理](workflow-agent-phases.md)。

## 条件、重复、恢复和输出

- 条件：`变量【名称】` 与参数、变量、数字或 `【文字】` 比较。
- 运算：为空、不为空、等于、不等于、包含、大于、大于等于、小于、小于等于。
- 分支动作：设置变量、跳到步骤、停止流程。
- 重复：必须同时声明目标步骤、“直到”条件和大于 0 的最大次数。
- 语言 3 失败策略：本步有界重试/检查，以及已声明的继续、重新执行、重新验证、恢复、跳转、等待或停止。
- `保存为：变量【名称】` 保存步骤结果；`输出` 逐字段绑定当前时间、变量、参数或文字常量。
- 有输出必须声明“保存结果”权限。

## 规则与程序扩展

参数 = 每次运行可能需要校准的“旋钮”（等待时长、次数、按钮位置、偏移、颜色值）；规则 = 流程作者
一次定义好、描述目标软件业务事实的配置（区域映射、分类标签、菜单动作、循环策略）。判定标准：
每次运行可能要改的 → 参数；流程作者定义一次、稳定不变的业务事实 → 规则。
规则是流程包自己的可读配置。复杂的重复界面模式可增加一个受限的 `workflow.py`：

```markdown
## 规则

### 规则名称

- 区域：区域【统计区域】
- 标签：今日=today；本周=week

## 程序扩展

- 文件：workflow.py
- 入口：run
- 用途：按上述规则读取统计区域。

## 执行步骤

### 执行规则

- 执行：执行程序扩展
- 逐项输出：是
```

应用名称、文字、坐标、HSV、分类、菜单动作和循环策略必须保留在流程包的声明（参数或规则）中；
平台代码只提供公共原子能力。程序扩展只能使用 `ctx` SDK，不能直接调用屏幕/系统库。逐项输出使用
`当前结果【字段】` 绑定输出。影响数据的流程通过步骤观察、最终确认和失败策略控制风险；不要用强制人工选窗替代唯一候选自动确认规则。

程序扩展必须使用以下形态：

```python
def run(ctx):
    rule = ctx.manifest["flow"]["task_rules"]["规则名称"]
    previous = ctx.vars.get("前一步保存的变量")
    ctx.stop.check()
    # 只通过 ctx.ocr、ctx.screen、ctx.geometry、ctx.window、ctx.mouse、ctx.browser 等公共能力工作
    yield {"result": "可序列化结果"}
```

必须遵守：

- 入口函数是 `run(ctx)`，返回 `dict`、可迭代的 `dict` 或 `None`；
- `ctx.vars` 是此前步骤 `保存为` 结果的只读实时映射；`ctx.values` 仅解析参数与类型；
- 程序扩展使用 `ctx.debug.log("说明", level="info")` 写本次运行诊断，不自行打开文件；底座把未捕获
  异常及 traceback 写入运行日志。日志不得包含 Cookie、密码或敏感页面正文；
- 每轮循环调用 `ctx.stop.check()`，循环次数从 `workflow.md` 读取并有上限；
- 鼠标键盘组合动作放在 `ctx.input.transaction()` 中；
- 影响界面的动作使用 `ctx.step.perform()` 并以重新读屏作为成功条件；成功条件不得恒为 `True`；
- 需要用户观察的节点使用 `ctx.debug.step()`；
- 可调点、区域、颜色、文字、正则、分类、菜单名称、等待和上限从规则读取；
- 不导入或直接调用屏幕、窗口、网络、子进程和操作系统控制库；
- 失败时保留流程打开的应用和浏览器现场；只有流程明确声明关闭时才关闭，不得关闭无法唯一确认的窗口。

临时菜单或确认框必须声明并实现交互事务：

```markdown
- 交互锁开始：打开快捷菜单之前
- 交互锁结束：确认框关闭之后
- 等待交互锁：DURATION(30s)
- 菜单验证超时：DURATION(6s)
```

能用交互模板表达的场景优先使用交互模板，底座已把“打开—识别—选择—确认”包成交互事务；
只有模板表达不了的自定义交互，才在程序扩展中手写交互锁字段并传给 `ctx.input.transaction`。

交互锁只协调多个自动化流程，不锁住用户本人。开始和结束必须成对写入 `workflow.md`，并作为
`start`、`end` 参数传给 `ctx.input.transaction`；SDK 在进入和退出真实事务时记录它们。
`等待交互锁秒数` 只限制排队时间，不会定时解锁。事务持有时间由真实代码边界及内部有限验证超时
限制。只读识别和普通等待不得包在长事务中。同一截图区域需要匹配多个候选文字时，必须一次 OCR
后在内存中匹配全部候选，禁止为每个候选文字重复截图。

## 权限

登记名称：读取屏幕、点击屏幕/操作鼠标、操作键盘、读取剪贴板、写入剪贴板、读取文件、
保存结果/写入文件、控制应用、读取浏览器、操作浏览器、浏览器下载、管理浏览器会话。
只声明最低权限，但不能少于真实动作需要的权限；任何浏览器权限都必须同时声明
`browser-enhancement@1`。

## 开发和验收

1. 先确认目标、完成标志、禁止动作、输出和失败边界。
2. 验证锚定窗口规则：唯一候选自动确认；多个候选显示虚线框由用户选择。
3. 先验证只读识别，再模拟运行，再由用户监督一次安全操作。
4. 测试一条数据、停止、重试、重新选择、跳过和最大循环边界。
5. 安装并校验流程后运行 `cli health --workflow <流程标识>`，首次真实运行由用户监督。
6. 向用户展示真实自然语言步骤、权限、输出、测试范围和回退方式。

## `inspect`、`validate` 和真实验收

修改已安装流程前，先用 `workflow show <标识>` 读取 `_meta.package_dir`，把整个流程包复制到独立草稿
目录；不得只复制 `workflow.md`，因为包内可能还有 `workflow.py`、资源和测试。在草稿中修改并提升
版本后依次运行：

```powershell
& $AppCli cli workflow inspect <流程包目录>
& $AppCli cli workflow install <流程包目录>
& $AppCli cli workflow validate <流程标识>
```

`inspect` 接受本地目录、ZIP 或 workflow.md 路径；`validate` 接受已安装流程的标识，不能传包路径。

不得把已安装目录本身作为 `workflow install` 的源目录；底座会在移动任何文件前拒绝这种自覆盖安装。
直接编辑已安装的用户流程会立即生效，只适合人工修复，编辑后仅运行 `inspect` 校验，不再对同一目录
执行 `install`。内置流程的 `_meta.readonly` 为 `true`，必须复制为独立草稿或用户副本后修改。

校验会检查：

- Markdown 章节、字段和中文命令是否属于当前语言；
- 标识、语义版本、坐标边界和具名引用是否有效；
- 动作使用的权限是否已经声明；
- 修改页面的步骤是否有操作前观察和操作后验证；
- 条件、循环、重试和失败策略是否有合法边界；
- 程序扩展文件、入口、导入、`ctx` 权限及危险调用是否合规；
- 输出是否有稳定字段并声明保存结果权限。

校验不会检查目标软件当前版本、坐标是否落在真实按钮上、HSV 是否准确、文字是否能被当前截图识别，
也不会证明完整业务流程已经成功。这些只能通过只读观察和用户监督的真实页面运行验收。

## WorkBuddy 交付前逐项复核

1. 从头读取一遍生成的 `workflow.md`，确认普通用户能说出每个步骤做什么。
2. 搜索 `workflow.py` 中的数字、字符串和正则；可配置的业务值集中到 `workflow.md`。
3. 搜索每个 `ctx.mouse`、`ctx.keyboard` 调用，确认前置页面状态和操作后验证都存在。
4. 搜索 `while` 和 `for`，确认停止检查、业务结束条件和最大次数都存在。
5. 故意制造一次目标缺失、文字未识别和窗口关闭，确认流程会等待、重新选择、跳过或停止。
6. 安装测试副本，由用户监督验收一条安全的真实业务数据。

当前 Markdown 格式允许流程包根目录中一个显式声明并通过权限/源码校验的 Python 扩展。只有跨流程公共
能力才进入 SDK；具体软件的页面判断、分类和步骤组合留在流程包。未公开的公共能力不自行虚构。


## 智能恢复与终止收尾

先读 [阶段契约](workflow-agent-phases.md)：语言 3 把 Agent 判断、已知错误和恢复路线写在当前步骤，
恢复步骤放在“执行步骤”中并声明 `用途：恢复处理`。恢复后重新验证，不盲目重放有副作用的动作。
正常业务结果继续使用分支。安全拒绝、能力不可用和用户停止不得被 Agent 放行。

结束处理需要 `workflow.lifecycle@1` / `workflow-lifecycle@1`，读取 [生命周期](workflow-lifecycle.md)。
区分停止请求、stopping、finalizing 和进程实际退出；`stopped:false` 不能报告为已停止。
