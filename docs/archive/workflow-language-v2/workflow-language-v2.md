# 既有流程语言 2 的兼容与迁移

仅在维护既有语言 2 流程或当前安装版不支持语言 3 时读取。先查询安装版能力、schema 和 SDK，
再用同一安装版 validate；不要把语言 3 标记加到旧规则上当作迁移完成。
新流程在能力满足时使用 [语言 3](workflow-agent-phases.md)。

- 旧 `执行者：agent` 和 `agent-checkpoint@1` 对应整步交接；语言 3 改为各阶段 `方式：Agent`。
- 全局“异常处理”、旧默认 VLM、旧步骤恢复与 [异常规则](exception-handling.md) 只用于语言 2。
- 全局“例外异常”迁入对应步骤的 `失败 → 遇到【名称】`；[结束处理](workflow-lifecycle.md) 继续保留。
- `vlm-choice@1` 只作 [旧选择判断](workflow-vlm-choice.md)；新流程使用 `失败 → 仍失败：Agent`。
- [异常重启](exception-restart.md) 默认关闭，只支持语言 2；语言 3 不隐式从头重跑。

程序动作、区域、SDK、业务分支和输出仍可复用。迁移时逐步比较观察、动作、验证、失败去向和收尾，
涉及发送、支付、提交或删除时保留去重和验证，不能仅验证语法。

## 错误留图与自定义纠错（小助手 1.2.9 起）

Markdown 和 Python SDK 流程因异常退出时自动尝试保存绑定窗口截图和错误说明；主动停止不截图，窗口不可见或身份不明确时只记录截图失败原因，不扩大到整个桌面。

普通操作步骤可以声明：

```markdown
- 异常恢复：步骤【判断异常页面】
- 预期页面：文章详情
- 最多恢复次数：2 次
```

目标可以是普通 engine 判断步骤，或只请求截图、未授权操作的 Agent 步骤。使用 `异常恢复现场.failed_step/error_type/error` 按错误或页面状态跳转到用户定义的处理步骤。已知错误进入相应处理；需要视觉判断时交给 Agent；未知、不确定、超限时停止并保留现场。后台输入安全拒绝和用户停止不自动恢复。

“预期页面”提供原本目标，不限制 VLM 回答是/否。一次观察可返回多个分类与字段，例如：

```json
{"observation":{"page":"图片放大","menu":"无","confidence":0.95,"reason":"文章图片占满右栏"}}
```

流程声明 `结果格式：observation=OBJECT`，根据返回对象分别跳转。Agent 仅判断，后续流程执行明确动作并验证。通过 engine 纠错入口再进入 Agent 时，失败现场仍作为观察上下文附带。窗口宽度等可确定的几何数据直接由锚定窗口计算，不为此启动 Agent。


### Agent 接管与步骤级操作授权

动态步骤可以声明 `执行者：agent`，并在基本信息声明 `引擎能力：agent-checkpoint@1`：

```markdown
### 判断或操作当前页面

- 执行者：agent
- 指令：确认当前页面状态，并按流程目标处理唯一目标
- 请求观察：截图、OCR、UI 元素
- 允许操作：屏幕操作
- 结果格式：completed=BOOLEAN
- 超时：120 秒
- 失败：停止
```

`请求观察` 必填，但只描述允许按需读取的观察类型，不能解释为操作授权。`允许操作` 可省略；
当前只登记 `屏幕操作`，省略时 Agent 不得改变屏幕。步骤还必须声明结果格式、有限超时和失败策略，
不能同时包含固定 `动作`、条件分支、有界重复或新窗口登记。

DSH Provider 只有在兼容插件能够证明任务级工具过滤时才可接受 `屏幕操作`。`dsh-screen-automation`
0.1.6 源码已提供策略版本和精确白名单的执行时校验；在兼容版本完成发布、安装和连接验证前，
Provider 仍默认拒绝真实屏幕操作，不得靠提示词、手工环境变量或未经验证的版本号冒充权限隔离。
同一 Provider 递归触发 checkpoint 时会返回 `recursive_agent_call`，流程应停止并让用户重新设计
边界，不得自动重试。

Provider 能力必须在运行时探测。WorkBuddy 中安装本 Skill，只证明 Agent 可以主动调用小助手，
不证明小助手具备反向创建 WorkBuddy 任务的授权。外部 Provider 不可用时，可以使用平台明确报告
为可用的小助手官方智能服务；免费版、专业版、组件未安装、未授权和平台不支持必须分别解释。

Windows 与 macOS 用户都通过“设置 → Agent 接入”管理自动分派。连接测试后至少运行一次只读 Agent 步骤，
确认 checkpoint 经 Provider 返回严格结果并恢复流程；不得把 Provider 版本探测成功当作纵向闭环。
CLI 的 `agent status` 只显示非秘密配置摘要，`agent probe` 只探测已配置 Provider；二者不得修改设置或接收
凭据，也不能替代 checkpoint 闭环验收。


## 可选目标与失败去向


「点击操作区域【区域】中的文字【文字】」和「点击区域【命名区域】中的文字【文字】」这类**原生 OCR 文字点击**动作，本身会先在区域里找文字、找不到立即判失败。配合 `失败` 字段，可以让「没检测到文字」按预期流转，而不是走全局异常处理（等待手动恢复）。

| 场景 | 推荐失败命令 | 行为 |
|---|---|---|
| 文字可能没出现（已领过、无内容、条件分支点） | `失败：跳过当前步骤` | 跳过本步，继续下一步 |
| 找不到就要走另一条路径（去读余额、走兜底分支） | `失败：跳到步骤【目标步骤】` | 直接跳到指定步骤 |
| 页面可能在加载，想再试几次 | `失败：等待 1 秒；重试 3 次；仍失败则跳过` | 先重试，仍找不到再跳过 |
| 文字是关键确认标志，找不到按计划结束 | `失败：停止` | 正常结束并执行结束处理；不写失败策略则保留平台异常处理 |

示例：

```markdown
### 点击「立即领取」（点不到说明已领过或无可领积分）

- 操作区域：内容
- 动作：点击区域【菜单区域】中的文字【立即领取】
- 失败：跳到步骤【确认领取后余额】（未出现「立即领取」即不领取）

### 点击可选的「关闭广告」按钮（没有就不点）

- 操作区域：内容
- 动作：点击操作区域【内容】中的文字【关闭广告】
- 失败：跳过当前步骤
```

要点：
- `失败：跳过当前步骤` 和 `失败：跳到步骤【...】` 都能让 OCR 找不到文字的步骤**不进入全局异常处理**，直接按配置流转。
- **正常未匹配先执行步骤失败去向**：OCR 成功执行但没有找到可选文字、观察或验证条件不成立时，直接执行配置的跳过或跳转，不调用兜底 VLM。`失败：等待 2 秒；重试 3 次；仍失败跳到步骤【读取余额】` 同样有效；次数用完只是有界循环结束，随后执行指定去向。
- 明确写了 `仍失败停止` 时按配置结束流程，并执行“结束处理”；仅有重试次数而没有最终去向时，不把它推断为跳过或正常结束，保留平台异常处理。
- 截图、OCR 服务执行错误、窗口丢失、权限拒绝及程序扩展异常不是“没有找到文字”，不能套用普通未匹配分支；它们仍按例外异常、已配置恢复或平台 VLM 处理。`如果／则／否则` 适合显式表达预期的成功与不成功两条业务路径。
- 动作本身的 OCR 找字已经起到「先检验」作用，通常不需要再单独写 `验证` 字段。
- `失败：询问用户` 会弹窗让你当场选「重试 / 跳过 / 停止」，适合偶发但需人工判断的情况。
